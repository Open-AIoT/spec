## 1. 引言

### 1.1 目的

本规范定义设备能力模型（Device Capability Model）：一种与厂商、协议、云平台无关的设备能力描述格式。它回答一个问题：**一台设备如何以标准化方式描述"我有什么属性、能执行什么动作、会产生什么事件"**，使任何平台与任何 AI 智能体（Agent）在不经人工对接的前提下理解并（经授权后）使用该设备。

### 1.2 范围

本规范覆盖：实体层次模型（产品/设备/分组/标签）；交互原语（属性/动作/事件/能力块）；数据类型系统；单位与量纲；标识符与命名；语义标注；设备影子与在线状态的模型级语义；能力组合与继承；描述文本双语内建；扩展机制。

### 1.3 非目标

以下内容**不在**本规范范围，由对应层规范定义：

1. 协议绑定（如何把能力渲染为 MCP tools、OpenAPI 路径等）——属 L1 协议绑定规范。本规范不依赖任何具体协议；替换任一绑定协议不应导致本规范任何条款变动。
2. 鉴权、授权、凭据分级、确认流程与审计——属 L2 授权与安全规范。本规范仅定义安全**标注**的词汇表（见 §8），不定义凭据体系。
3. 设备接入链路、OTA、规则引擎、数据存储——属各平台自身实现。
4. 具体设备品类的标准能力库——v0.x 阶段不维护官方能力块注册库（见 TBD-7）。

### 1.4 厂商中立声明（规范性）

符合本规范的设备与平台**不得**被要求运行任何特定厂商的云平台、SDK 或许可证。本规范不含、且后续版本不得引入任何将合规性与特定厂商产品绑定的条款。参考实现信息见附录 B（非规范性）。

## 2. 元约定

### 2.1 约束级别用词

本规范中，**必须（MUST）**、**不得（MUST NOT）**、**应当（SHOULD）**、**不应当（SHOULD NOT）**、**可以（MAY）** 为约束级别用词，含义如下（对齐 RFC 2119/8174 惯例）：

- **必须 / 不得**：无条件要求或禁止；违反即不合规。
- **应当 / 不应当**：默认要求或禁止；仅在存在充分理由时可偏离，偏离方必须理解并承担后果。
- **可以**：可选；实现方可自由决定。

### 2.2 前向兼容义务（must-ignore）

1. 消费方（读取能力描述的任何实现）**必须**忽略其不认识的字段，且**不得**因此报错或拒绝解析。
2. 消费方**必须**忽略其不认识的枚举值、标注键与扩展命名空间内容。
3. 模型定义方**不得**依赖消费方识别任何可选字段来实现核心语义。

### 2.3 演进纪律

1. 本规范遵循 `VERSIONING.md`：同一主版本内只增不删（additive-only）；必填字段冻结；弃用须经公示期；破坏性变更仅经 RFC 通道。
2. 模型文档（能力描述文件）头部**必须**携带 `specVersion` 字段，声明其依据的规范版本。
3. 规范演进与设备能力演进为两条时间线：能力块独立携带 `version`（见 §4.4、§10），与 `specVersion` 无关。

### 2.4 序列化与元 schema

1. 能力描述的权威序列化为 **JSON**（RFC 8259）。可以（MAY）提供 YAML 等编辑形态，但其语义必须以 JSON 序列化为准。
2. 本规范以 **JSON Schema draft 2020-12** 定义各文档结构的元 schema（随规范发布于 `schemas/` 目录）；合规的能力描述**必须**通过相应元 schema 校验。
3. 字段名区分大小写；未在本规范中出现的字段视为未知字段，适用 §2.2。

### 2.5 保留前缀

以下前缀由本规范保留，模型定义方**不得**另作他用：

- `$`：平台维护的元属性与元字段（见 §9.2）；
- `x-<vendor>.`：厂商扩展字段（见 §12）；
- 其余保留项：**TBD**（保留字清单见未决事项，v0.x 期间以本节两项为准）。

## 3. 信息模型：实体与层次

### 3.1 实体总览

```
命名空间（Namespace，§7）
  └─ 产品（Product）：一类设备的能力模板——能力的定义点
       └─ 设备（Device）：产品模板的一个实例——能力的呈现点
分组（Group）/ 标签（Tag）：设备的横向组织维度
```

1. **产品（Product）必须**是能力的唯一定义点；**设备（Device）必须**继承其产品模板的能力集合（裁剪与增强规则见 §10）。
2. 分组与标签**必须不**承载能力定义；它们仅用于设备的批量定位与管理（如"所有贴有 `车间A` 标签的设备"）。
3. 分组/标签的精确形态（分组可否嵌套、标签是否键值化）及其与授权范围的对应关系：**TBD**（TBD-2，属 L2 协同决策）。v0.x 期间实现方**不得**在能力描述中编码分组/标签的语义。

### 3.2 产品文档（最小示例）

产品文档是能力模型的顶层文档：

```json
{
  "specVersion": "0.1.0-draft",
  "type": "product",
  "id": "https://acme.example/products/thermostat-t1000",
  "name": "thermostat-t1000",
  "title": { "en": "Thermostat T1000", "zh-CN": "温控器 T1000" },
  "description": {
    "en": "A wall-mounted thermostat with temperature sensing and setpoint control.",
    "zh-CN": "壁挂式温控器，具备温度感知与目标温度设定能力。"
  },
  "capabilities": [
    "https://acme.example/ns/cap/temperature-sensing/1.0",
    "https://acme.example/ns/cap/setpoint-control/1.0"
  ]
}
```

约束：

1. `specVersion`、`type`、`id`、`name`、`title`、`capabilities` 为**必须**字段；`description` 为**应当**字段。
2. `id` 规则见 §7；`capabilities` 数组的每一项**必须**为能力块的版本化 URI（§7.3、§10.2）。

### 3.3 设备实例文档（最小示例）

```json
{
  "specVersion": "0.1.0-draft",
  "type": "device",
  "id": "https://acme.example/devices/01JEXAMPLE0000000000000001",
  "name": "meeting-room-3f-thermostat",
  "product": "https://acme.example/products/thermostat-t1000",
  "title": { "en": "3F Meeting Room Thermostat", "zh-CN": "三楼会议室温控器" },
  "capabilityOverrides": {
    "omit": ["https://acme.example/ns/cap/setpoint-control/1.0#childLock"]
  }
}
```

约束：

1. `product` **必须**引用产品文档 `id`；实例默认完整呈现模板能力。
2. `capabilityOverrides.omit` 仅**可以**裁剪产品模板中声明为可选（`"required": false`）的能力项；必选能力**不得**裁剪（§10.3）。
3. 设备实例标识的生成算法不受本规范约束（UUID、雪花 ID 等均可），但**必须**全局唯一且永不变更（§7.2）。

## 4. 交互原语：属性 / 动作 / 事件 / 能力块

### 4.0 通则

1. 能力模型由三种交互原语——**属性（Property）、动作（Action）、事件（Event）**——与一种组合容器——**能力块（Capability）**——构成。不引入第五种原语。
2. 三种原语均**必须**携带：`id`（块内局部名，§7.4）、`type`、数据 schema（§5）；均**应当**携带：`title`/`description` 双语对象（§11）、`annotations`（§8）、`examples`。
3. 原语的局部名在同一能力块内**必须**唯一；跨块引用以 `能力块URI#局部名` 形式（§7.4）。

### 4.1 属性（Property）

属性表示设备可观察、可设置的状态。

1. 属性的读与写是两个独立语义，**必须**分别以 `access.read` / `access.write` 声明；只写属性（`writeOnly`，如下发配置但不回读）合法存在。
2. 只读属性**不得**出现在任何"写"语义的渲染结果中。
3. 属性值**必须**带时间戳语义：消费方读取属性时获得的是某时刻的快照（影子语义见 §9）。

最小示例：

```json
{
  "id": "temperature",
  "type": "property",
  "title": { "en": "Current temperature", "zh-CN": "当前温度" },
  "description": {
    "en": "Measured ambient temperature. Read-only.",
    "zh-CN": "实测环境温度。只读。"
  },
  "schema": {
    "type": "number",
    "minimum": -40,
    "maximum": 85,
    "unit": "Cel"
  },
  "access": { "read": true, "write": false },
  "examples": [23.5]
}
```

### 4.2 动作（Action）

动作表示请求设备执行一件事。

1. 动作**必须**声明入参 schema（`input`，无入参时省略）与出参 schema（`output`，无返回时省略）。
2. 动作**必须**声明执行时长语义：`execution` 为 `"sync"` 或 `"async"`；`"sync"` 动作**应当**给出 `timeoutHint`（毫秒，预期上限）。
3. 耗时超过秒级的动作**应当**建模为"异步动作 + 完成事件"（动作返回受理结果，事件通知完成），而非同步长阻塞。
4. 动作的安全标注（`destructive`、`idempotent`、`requiresConfirmation`）见 §8.2；破坏性动作**必须**显式标注。

最小示例：

```json
{
  "id": "setTargetTemperature",
  "type": "action",
  "title": { "en": "Set target temperature", "zh-CN": "设定目标温度" },
  "description": {
    "en": "Sets the setpoint. Takes effect within seconds; idempotent.",
    "zh-CN": "设定目标温度，数秒内生效；重复调用结果相同（幂等）。"
  },
  "input": {
    "type": "object",
    "properties": {
      "target": { "type": "number", "minimum": 5, "maximum": 35, "unit": "Cel" }
    },
    "required": ["target"]
  },
  "output": {
    "type": "object",
    "properties": { "accepted": { "type": "boolean" } },
    "required": ["accepted"]
  },
  "execution": "sync",
  "timeoutHint": 3000,
  "annotations": { "destructive": false, "idempotent": true },
  "examples": [{ "input": { "target": 26 }, "output": { "accepted": true } }]
}
```

### 4.3 事件（Event）

事件表示设备主动产生的通知。

1. 事件**必须**声明负载 schema（`payload`，无负载时省略）。
2. 事件**应当**声明严重级别 `severity`：`"info"` / `"warning"` / `"critical"`；缺省视为 `"info"`。
3. 本规范只声明"事件存在、负载是什么"；事件的投递通道、订阅握手与重推机制属 L1 绑定层，本规范不定义。事件是否需要订阅才能收到：**TBD**（TBD-3）。

最小示例：

```json
{
  "id": "overheatingAlarm",
  "type": "event",
  "severity": "warning",
  "title": { "en": "Overheating alarm", "zh-CN": "过热告警" },
  "description": {
    "en": "Raised when the measured temperature exceeds the safety threshold.",
    "zh-CN": "实测温度超过安全阈值时触发。"
  },
  "payload": {
    "type": "object",
    "properties": {
      "temperature": { "type": "number", "unit": "Cel" },
      "threshold": { "type": "number", "unit": "Cel" }
    },
    "required": ["temperature", "threshold"]
  }
}
```

### 4.4 能力块（Capability）

能力块是一组围绕同一功能域的属性/动作/事件的可复用、可版本化组合（类比 Matter cluster）。

```json
{
  "specVersion": "0.1.0-draft",
  "type": "capability",
  "id": "https://acme.example/ns/cap/setpoint-control",
  "version": "1.0",
  "title": { "en": "Setpoint Control", "zh-CN": "目标温度控制" },
  "required": false,
  "affordances": {
    "targetTemperature": { "type": "property", "...": "..." },
    "setTargetTemperature": { "type": "action", "...": "..." }
  }
}
```

约束：

1. 能力块**必须**携带 `version`（语义化版本，独立于 `specVersion`）；引用时**必须**使用版本化 URI（§7.3）。
2. 能力块**应当**聚焦单一功能域；一个块内的原语**应当**能共同回答"这块功能是什么"。
3. 能力块**可以**被多个产品引用；块的语义**不得**因引用它的产品不同而改变。

## 5. 数据类型系统

### 5.1 基座

1. 类型系统以 JSON Schema draft 2020-12 为基座：允许使用 `type`、`properties`、`required`、`items`、`enum`、`minimum`/`maximum`、`minLength`/`maxLength`、`minItems`/`maxItems`、`default`、`format` 等关键字。
2. 本规范**不**自造 schema 方言；下表以外的扩展关键字**必须**以厂商扩展机制（§12）引入。

### 5.2 IoT 扩展关键字（规范性清单）

| 关键字 | 适用 | 含义 | 级别 |
|---|---|---|---|
| `unit` | number/integer | UCUM 单位代码（§6） | 有单位的数值**必须**携带 |
| `quantityKind` | number/integer | 量纲标识（QUDT IRI 或等价标识） | 可以 |
| `enumLabels` | enum | 每个枚举值的双语文案对象（§5.4、§11） | 枚举**应当**携带 |
| `step` | number/integer | 步进约束 | 可以 |

### 5.3 类型纪律

1. **整数与浮点必须区分**：`"type": "integer"` 与 `"type": "number"` 语义不同，定义方**不得**混用（JSON 自身不区分，IoT 语义必须区分）。
2. **时间**一律以 `"type": "string", "format": "date-time"`（RFC 3339）表达，且**必须**携带时区偏移；**不得**使用 Unix 时间戳数字作为对外语义（内部实现随意）。
3. 数值的取值范围（`minimum`/`maximum`）**应当**显式声明；缺省视为无约束。
4. 结构体嵌套深度**应当**不超过 3 层；数组**应当**声明元素类型。
5. 二进制/字节串：v0.1 不提供标准类型；如确需，以 base64 字符串 + `"contentEncoding": "base64"` 表达。是否引入一等二进制类型：**TBD**（TBD-5）。

### 5.4 枚举

1. 枚举值的**取值集合**用 JSON Schema `enum` 表达；每个值的双语文案用 `enumLabels` 表达（见下例）。
2. 枚举值**必须**为英文机器可读 token（`lowerCamelCase`）；展示文案**不得**充当取值。
3. 设备实例能否在模板枚举集合基础上收窄取值：**TBD**（TBD-9）；v0.x 期间**不得**收窄。

```json
{
  "type": "string",
  "enum": ["cool", "heat", "auto"],
  "enumLabels": {
    "cool": { "en": "Cooling", "zh-CN": "制冷" },
    "heat": { "en": "Heating", "zh-CN": "制热" },
    "auto": { "en": "Auto", "zh-CN": "自动" }
  }
}
```

## 6. 单位与量纲

1. 数值型属性与参数的物理单位**必须**以 `unit` 字段携带 **UCUM** 代码（大小写敏感，如 `Cel`、`kg/m3`、`kWh`）。UCUM 为权威表示；**不得**自造单位字符串、**不得**以中文/符号文案（如"℃"）充当单位字段值。
2. 展示用单位文案**可以**经 §11 的双语字段另行提供。
3. 量纲（quantityKind）**可以**以 `quantityKind` 字段携带 QUDT IRI（如 `http://qudt.org/vocab/quantitykind/Temperature`），供需要本体推理与跨单位换算的系统使用；缺省不影响合规。
4. 复合单位**必须**为合法 UCUM 表达式；实现方校验 UCUM 语法时可以（MAY）限制在 UCUM 常用子集，但**不得**拒绝合法 UCUM 代码之外的值——不认识的合法代码按未知字段纪律（§2.2）放行。
5. 无单位数值（比值、计数）**应当**省略 `unit`，或显式使用 UCUM 无量纲代码 `1`。

## 7. 标识符与命名

### 7.1 标识符与名称分离（核心纪律）

1. 每个实体与能力**必须**同时具有：`id`（标识符：稳定、不透明、永不复用）与 `name`（名称：人类可读、可以变更）。
2. 消费方**必须**以 `id` 为关联键；**不得**以 `name` 做持久关联——名称可改，改名不构成破坏性变更。
3. `id` 的不透明性：消费方**不得**从 `id` 字符串解析语义（路径段无约定含义，§7.3 的版本段除外）。

### 7.2 标识符形式

1. 标识符**必须**为可解析 HTTPS URI（2026-09-09 决策）。
2. 标准命名空间前缀为 `https://open-aiot.com/ns/`；厂商实体**应当**使用自有域名的 HTTPS URI（如 `https://acme.example/products/...`），**不得**占用标准命名空间。
3. 设备/产品实例 `id` 的生成算法不受约束（UUID、雪花 ID 等均可），但**必须**全局唯一且永不变更；标识符**不得**复用（实体删除后其 `id` 永久退役）。

### 7.3 能力块 URI 与版本

能力块的版本化引用形式为 `{块URI}/{version}`，原语级引用为 `{块URI}/{version}#{局部名}`，例如：

```
https://acme.example/ns/cap/setpoint-control/1.0
https://acme.example/ns/cap/setpoint-control/1.0#setTargetTemperature
```

### 7.4 命名规范（面向 LLM）

1. 局部名**必须**为英文 `lowerCamelCase`。
2. 动作名**必须**以动词开头（`setTargetTemperature`，而非 `temperatureSet`）；属性名**应当**为名词短语；事件名**应当**为"名词+过去分词/Alarm/Changed"类可辨识形态。
3. **不得**使用有歧义的缩写（`tmp` 不可，`temp` 亦不应当）；`min/max/cur/target` 之外的全拼优先。
4. 保留字与前缀见 §2.5；其余保留字清单：**TBD**。

## 8. 语义标注

### 8.1 双层语义结构

1. 本规范提供**内建标注词汇表**（本节，规范性）与**外部语义链接**（§8.3，机制性）两层语义；**不**自建本体。
2. 内建标注缺失时，结构（schema 层）**必须**仍完整可用；标注不得替代结构。

### 8.2 内建标注词汇表（`annotations` 对象）

| 键 | 类型 | 含义 | 级别 |
|---|---|---|---|
| `readOnly` | boolean | 该交互不改变设备状态（属性读、只读动作） | 应当 |
| `destructive` | boolean | 不可逆或影响物理状态/数据的操作 | 破坏性操作**必须** |
| `idempotent` | boolean | 重复调用与单次调用效果相同 | 应当 |
| `requiresConfirmation` | boolean | 提示消费方：执行前应经人在环路确认（确认语义与流程属 L2） | 应当 |
| `openWorld` | boolean | 返回值集合可能超出已声明枚举 | 可以 |

约束：

1. 标注键的词汇表以本表为准；新增标准标注键仅经规范 MINOR 版本 additive 引入。
2. 标注是**提示（hint）**，不构成安全保证；授权决策的依据是 L2 凭据体系，不是标注。

### 8.3 外部语义链接

1. 任何原语与能力块**可以**携带 `semanticTypes`：一个外部 IRI 数组，为该能力附加本体语义（如 QUDT quantityKind、SDF quality name、未来社区词汇表）。
2. 消费方**不得**因不认识其中任何 IRI 而报错（§2.2）；推荐的 IRI 来源清单：**TBD**（TBD-10），v0.x 仅定义机制。
3. 本规范**不**采纳 iotschema.org 作为权威来源（该项目已停滞）；不依赖 JSON-LD 处理栈。

### 8.4 与 AI 工具描述的映射约定（为绑定层预留）

模型层字段与 AI 工具描述之间**必须**存在确定性映射，使绑定层渲染为机械翻译而非二次创作。本规范为此要求：

1. 动作局部名 → 工具名的映射原料（§7.4 命名纪律即为此服务）；
2. `title`/`description` 双语对象 → 工具描述（§11）；
3. `input` schema → 工具入参 schema（JSON Schema 直出）；
4. §8.2 标注 → 工具标注（`readOnly`/`destructive`/`idempotent` 与主流工具标注语义同源）；
5. `examples` → 工具描述中的示例。

具体映射规则由 L1 绑定规范定义；本规范保证上述原料字段的存在性与稳定性。

## 9. 设备影子与在线状态

### 9.1 影子语义

1. 影子（Shadow）是属性值的**运行时投影**，含两部分：`reported`（设备上报的最新值）与 `desired`（消费方期望、待设备收敛的值）。
2. 影子中的每个值**必须**携带 `value`、`updatedAt`（RFC 3339，带偏移）与 `version`（单调递增整数，用于乐观并发）。
3. `desired` 与 `reported` 收敛的判断、离线设备的 `desired` 下发时机与冲突解决的完整语义：**TBD**（TBD-8）；v0.1 只定义字段与投影关系。
4. 影子的存储、同步与传输协议不属本规范。

```json
{
  "deviceId": "https://acme.example/devices/01JEXAMPLE0000000000000001",
  "shadow": {
    "reported": {
      "temperature": { "value": 23.5, "updatedAt": "2026-09-09T10:15:30+08:00", "version": 12 }
    },
    "desired": {
      "targetTemperature": { "value": 26, "updatedAt": "2026-09-09T10:14:02+08:00", "version": 3 }
    }
  }
}
```

### 9.2 在线状态（保留元属性）

1. 在线状态**必须**建模为平台维护的保留元属性，而非设备上报的普通属性；本规范保留 `$` 前缀命名空间：
   - `$online`：boolean，设备当前在线；
   - `$lastSeenAt`：date-time，最后一次与平台通信时刻。
2. 设备模型**不得**自行定义 `$` 前缀字段；平台**不得**以普通属性冒充在线状态。

### 9.3 离线读取的新鲜度纪律

1. 设备离线时读取属性，返回的**必须**是影子值并附带新鲜度信息（`updatedAt` 及/或派生的 `stale` 标记）；**不得**静默返回过期值而不标注。
2. 设备离线且请求为"写"语义时，行为语义（写入 `desired` 待收敛 vs 拒绝）**应当**在响应中显式区分；具体响应结构属绑定层。
3. 设备首次上报前影子是否存在、初始值规则：**TBD**（并入 TBD-8）。

## 10. 组合与继承

### 10.1 组合优先

1. 产品**必须**以"引用若干能力块"的组合方式构建；本版本**不**提供产品间的多层级继承（无"基类产品→子类产品"关系）。该限制如被实践证明不足，仅以 additive 方式在后续主版本评估引入（TBD-6）。
2. 能力块是复用与版本化的最小单位（§4.4）。

### 10.2 模板 → 实例

1. 设备实例**必须**声明其 `product`；实例默认完整呈现模板能力。
2. 实例**可以**通过 `capabilityOverrides.omit` 裁剪模板中 `required: false` 的能力项（对应实际硬件缺失）；**不得**裁剪必选能力项。
3. 实例**可以**附加厂商扩展能力块（§12.3）；附加块**不得**改变模板已有能力的语义。

### 10.3 模板演进

1. 能力块 MINOR 升级**必须**遵循 additive-only（同 §2.3 引用之政策）。
2. 实例对模板版本的跟随策略（自动跟随 MINOR vs 显式锁定）：实例文档**可以**省略版本段以表示跟随最新 MINOR；**TBD**：锁定语义的精确形式（并入 TBD-6 一并评估）。

## 11. 描述文本与双语

1. `title` 与 `description` **必须**为结构化双语对象，形式为 `{ "en": "...", "zh-CN": "..." }`；至少 `en` **必须**存在，`zh-CN` **应当**存在。这不是翻译文件，是模型的一等结构字段。
2. 语言标记使用 BCP 47；后续语言以 additive 方式追加。
3. 必填级原语（`required: true` 的能力项）的 `title`/`description` **必须**双语齐全；扩展字段（§12）的文案双语为建议。
4. 文案写作要求（面向调用它的 LLM 与开发者，而非设备工程师）：**应当**说明副作用、典型取值、与相邻能力的关系；`description` **应当**不超过 500 字符。
5. 本规范正文的权威语言：v0.x 为中文起草版，1.0 前完成英文权威版（已定决策）。

## 12. 扩展机制

### 12.1 扩展字段

1. 厂商扩展字段**必须**以 `x-<vendor>.` 前缀命名（如 `x-acme.calibrationDate`），置于所在对象的扩展位。
2. 扩展字段**不得**与标准字段同名冲突；**不得**改变所在对象中标准字段的语义。

### 12.2 扩展纪律

1. 扩展**不得**借用标准命名空间 `https://open-aiot.com/ns/`。
2. 扩展**不得**成为互操作的前置条件——"必须符合某扩展才算合规"的条款无效。
3. 消费方不认识扩展命名空间时**必须**忽略（§2.2 在扩展场景的重申）。

### 12.3 扩展能力块

1. 厂商扩展能力块**必须**以厂商自有域名 URI 承载（§7.2），结构同 §4.4。
2. 成功的扩展**可以**经 RFC 流程收编为标准字段或标准能力块（晋升通道见治理文件）。

### 12.4 弃用

字段、枚举值、能力块的弃用**必须**遵循 `VERSIONING.md` 流程：标记 `deprecated` → 至少保留一个完整 MINOR 周期并公示 → 方可在下一主版本移除。
