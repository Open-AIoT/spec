## 1. 引言

### 1.1 目的

tools manifest 是**零 MCP 依赖的接入面**：供平台连接器与不实现 MCP 的 AI 平台直接消费的静态工具清单。后端把能力注册表渲染为 manifest 文档，消费方（连接器、MCP 适配器、网关）据以获得工具集的名称、描述与参数 schema，无须实现 MCP 协议栈。

本规范定义：manifest 的文档格式（OpenAPI 3.x 基底 + 策展扩展层）、从该基底渲染各 LLM 平台工具清单格式的规则、与其他绑定的对齐条款、端点与版本约定。

### 1.2 范围

覆盖：manifest 文档结构与扩展字段；策展（curation）语义；渲染为 function-calling（FC）格式与 Claude tool-use 格式的规则；端点命名与分发；版本演进。

### 1.3 非目标

1. 能力本身的定义——属 L0 能力模型规范；本规范的映射原料字段由 L0 §8.4 保证。
2. MCP 传输、生命周期与工具调用语义——属《MCP 绑定规范》。manifest 是**描述**层契约，不含调用协议；调用经各平台自有机制或后端 invoke 端点完成。
3. 工具描述文本的写作细则——属《工具描述写作规范（LLM-first）》，本规范以引用继承。
4. 鉴权与授权——属 L2 授权与安全规范；manifest 文档本身为公开描述（不含敏感信息），分发端点免鉴权。

### 1.4 厂商中立声明（规范性）

符合本规范的实现**不得**被要求运行任何特定厂商的云平台、SDK 或许可证。本规范不含、且后续版本不得引入任何将合规性与特定厂商产品绑定的条款。

### 1.5 命名说明（P10）

本项目与任何同名/近名公司无关联；项目名写作"开放AIoT（Open AIoT）"。本规范以中立术语 **function-calling（FC）格式** 指代业界公开发布的 `[{"type":"function","function":{"name","description","parameters"}}]` 工具清单 JSON 格式，不引用其发布方名称。机器可读标识同样遵守命名纪律（见 §7 端点命名条款）。

## 2. 元约定

### 2.1 约束级别用词

**必须（MUST）**、**不得（MUST NOT）**、**应当（SHOULD）**、**不应当（SHOULD NOT）**、**可以（MAY）** 为约束级别用词，含义对齐 RFC 2119/8174 惯例。

### 2.2 前向兼容义务（must-ignore）

manifest 文档的消费方**必须**忽略其不认识的字段与扩展（含不认识的 `x-` 前缀字段），且**不得**因此报错或拒绝解析。

### 2.3 规范演进

本规范遵循 `VERSIONING.md`：主版本内只增不删；必填字段冻结；弃用有公示期；破坏性变更仅经 RFC 通道。文档头部携带 `specVersion`。

## 3. 定位与绑定谱系

### 3.1 单一事实源（规范性）

1. manifest 与 MCP tools、REST/OpenAPI 端点**必须**从同一份能力注册表渲染；manifest **不得**引入注册表中不存在的语义。
2. 绑定之间出现分歧时，以注册表元数据为准：改绑定，不改语义（与《MCP 绑定规范》§4.1 同一条款的两端表述）。

### 3.2 三类产物与渲染关系

```
                 能力注册表（单一事实源）
                          │
                ┌─────────┴──────────┐
                ▼                    ▼
     REST/OpenAPI 绑定        tools manifest（本规范）
     （调用通道）              manifest 文档 = OpenAPI 3.x 基底
                                + x-openaiot-* 策展扩展层（§4）
                                          │ 渲染（§5）
                              ┌───────────┴───────────┐
                              ▼                       ▼
                    FC 格式静态 JSON          Claude tool-use 静态 JSON
                    （function 清单）          （tools 数组）
```

1. manifest 文档是**基底产物**；FC/Claude 两份静态 JSON 是**渲染产物**，必须可由 manifest 文档确定性导出，不得独立维护（§5）。
2. MCP 适配器（参考实现：Open-AIoT `mcp` 仓）是 manifest 的一等消费方：它把 manifest 渲染为 MCP `tools/list`——manifest 因此同时是后端与适配器之间的**版本化公开契约**（版本声明见 §7.3）。

### 3.3 策展纪律（规范性，拒绝全量盲转）

1. 进入 LLM 视野的工具集**必须**是策展后的子集：只有标记 `x-openaiot-tool: true` 的操作才进入 manifest 的 LLM 面（§4.2）。
2. 全量盲转（把全部 REST 端点不加筛选地变为工具）**不得**被视为符合本规范——它造成上下文污染与工具误选（生态教训，见子规划 02 §6.6）。
3. 进入 LLM 面的描述**必须**为面向 LLM 重写的文本（`x-openaiot-llm-description`），不经策展的程序员视角描述不得进入 LLM 面。
4. manifest 工具数**应当**保持小集合（目标：v1.0 核心工具 ≤ 20 个；工具分类与准入门槛见子规划 02 §6.5）。

## 4. 文档格式：OpenAPI 3.x 基底 + 策展扩展层

### 4.1 基底

1. manifest 文档**必须**为合法的 OpenAPI 3.x 文档（3.0 或 3.1；具体小版本对齐见 TBD-2）。
2. 选择 OpenAPI 基底的理由（非规范性）：可被现有 OpenAPI→MCP 转换器生态（各类网关与生成器）直接消费，工具链零成本复用；裸 OpenAPI 缺失的 LLM 语义由扩展层补齐。
3. 文档中每个进入 LLM 面的工具**必须**对应一个 operation（path + method）；operationId **必须**与工具名一致（命名约定见《MCP 绑定规范》§5：动词开头 snake_case，三处同名）。
4. 工具入参 schema **必须**完整表达于 operation 的 `requestBody`（JSON 对象 schema）与 `parameters`（path/query）；合并规则见 §5.3。
5. 基底文档可以同时承载 LLM 面与 REST 面（同一份 OpenAPI 文档两种消费），也**可以**分两份发布；取舍见 TBD-2。

### 4.2 策展扩展层（`x-openaiot-*` 字段）

以下扩展字段为开放AIoT 标准扩展，置于 operation 对象上（除注明外）：

| 字段 | 类型 | 含义 | 级别 |
|---|---|---|---|
| `x-openaiot-tool` | boolean | 是否进入 LLM 面（工具白名单）；缺省 `false` | LLM 面工具**必须**显式 `true` |
| `x-openaiot-llm-description` | object | 面向 LLM 重写的双语描述 `{"en":"...","zh-CN":"..."}`；覆盖程序员视角的 summary/description | LLM 面工具**必须**携带；写法**必须**符合《工具描述写作规范》全部"必须"级条款 |
| `x-openaiot-annotations` | object | 工具标注：`readOnlyHint`（bool，必填）/`destructiveHint`/`idempotentHint`（bool，为 true 时给出） | LLM 面工具**必须**携带 |
| `x-openaiot-hidden-params` | array of string | 对 LLM 隐藏、由连接器/宿主注入的参数名（如租户上下文）；渲染产物中**必须**从 schema 剔除 | 可以 |

约束：

1. 扩展字段**不得**改变基底 OpenAPI 字段的语义；`x-openaiot-*` 之外的项目级扩展**不得**新增（厂商自用扩展以 `x-<vendor>.` 前缀隔离，遵循 `VERSIONING.md` §6）。
2. `x-openaiot-annotations` 的安全前提与《MCP 绑定规范》§7.4 一致：标注是**不可信提示**，不构成授权依据。
3. 扩展字段在主流 OpenAPI→MCP 转换器中的透传行为需逐一验证（TBD-2）；验证未通过的转换器不妨碍本规范成立（渲染产物可由自有渲染器产出）。

### 4.3 最小示例（非规范性）

```yaml
openapi: 3.0.3
info:
  title: Demo backend tools
  version: 0.1.0
paths:
  /v1/tools/invoke#list_devices:        # path 形态仅为示意；operation 归属见 TBD-2
    post:
      operationId: list_devices
      x-openaiot-tool: true
      x-openaiot-annotations: { readOnlyHint: true, idempotentHint: true }
      x-openaiot-llm-description:
        en: "Lists devices page by page. ... To page: pass the previous response's next_cursor until it is empty. Read-only and idempotent."
        zh-CN: "分页列出设备。……翻页带上一次返回的 next_cursor，直到它为空串。只读、幂等。"
      requestBody:
        content:
          application/json:
            schema:
              type: object
              properties:
                q:      { type: string, description: "按名称模糊搜索 / Fuzzy search by name" }
                cursor: { type: string, description: "分页游标 / Pagination cursor" }
                limit:  { type: integer, default: 20, minimum: 1, maximum: 100 }
```

## 5. 渲染规则：manifest → FC / Claude 静态清单

### 5.1 通则

1. 渲染产物**必须**只含 `x-openaiot-tool: true` 的 operation；顺序**必须**按工具名升序（确定性排序，与《MCP 绑定规范》§4.4 一致）。
2. 渲染是机械翻译：渲染器**不得**改写 `x-openaiot-llm-description` 的文本内容。
3. 两份渲染产物的工具名、描述、参数 schema **必须**相互一致（仅字段布局不同）。

### 5.2 描述渲染

两种产物的描述**必须**为：`llm-description.en + "\n\n" + llm-description["zh-CN"]` 的拼接字符串（en 在前、zh-CN 在后——与《MCP 绑定规范》§4.3 的拼接约定一致）。

### 5.3 参数 schema 渲染

1. 工具的入参 schema **必须**合并为单个 JSON Schema 2020-12 对象：以 `requestBody` 的对象 schema 为基础，把未被 `x-openaiot-hidden-params` 隐藏的 path/query `parameters` 并入其 `properties` 与 `required`；被隐藏的参数**必须**从产物 schema 中剔除（由连接器注入）。
2. 无入参工具：**必须**渲染为 `{"type":"object","additionalProperties":false}`。
3. FC strict 模式兼容性（所有字段显式 `type`、required 硬约束子集）为**应当**级；是否升级为强制：**TBD**（TBD-1）。

### 5.4 FC 格式产物

```json
[{ "type": "function",
   "function": { "name": "<operationId>", "description": "<§5.2 拼接>", "parameters": "<§5.3 schema>" } }]
```

**可以**附带 `annotations` 扩展键（对象，内容同 `x-openaiot-annotations`）供 MCP 适配器等消费方透传；FC 格式消费方不认识该键时按 §2.2 忽略。

### 5.5 Claude 格式产物

```json
[{ "name": "<operationId>", "description": "<§5.2 拼接>", "input_schema": "<§5.3 schema>" }]
```

差异纪律：Claude 形态无统一 required 硬约束、靠描述软约束——参数必填性**必须**同时写进参数描述文本（《工具描述写作规范》TD-7 的既有义务在此重申）。

## 6. 与 MCP 绑定的对齐条款

1. **同源**：两绑定共享同一注册表与同一元数据契约（《MCP 绑定规范》§4.2）；manifest 的 `x-openaiot-*` 字段值与 MCP `tools/list` 的对应字段**必须**一致（名称、描述、schema、annotations）。
2. **同名同义**：工具名在 manifest、MCP、OpenAPI operationId 三处完全一致（《MCP 绑定规范》§5）。
3. **错误同形态**：manifest 不定义调用协议，但配合 manifest 使用的调用端点（invoke 类）**必须**沿用 problem+json 错误形态（`type`/`title`/`status`/`code`/`detail` 字段与《MCP 绑定规范》§8.2 同构同码表）。
4. **分页同参数**：列表型工具的 `cursor`/`limit` 参数名、`next_cursor` 终止语义与 cursor 不透明纪律与《MCP 绑定规范》§9 完全一致。

## 7. 端点、分发与版本

### 7.1 端点命名中立化（规范性，P10）

1. 本规范 1.0 定稿时，manifest 端点**必须**采用中立命名（不含任何第三方公司名字样）。候选形态（如 `/v1/tools/manifest.openapi.yaml` + `/v1/tools/fc.json` + `/v1/tools/claude.json`）的具体取值：**TBD**（TBD-3）。
2. 现存 `/v1/tools/openai.json` 端点（历史命名）**必须**作为过渡别名保留，至规范 1.0 前完成切换并按 `VERSIONING.md` §4 公示弃用。
3. manifest 各产物端点**必须**免鉴权公开挂载（与 `/openapi.json` 同级）——文档本身不含敏感信息；其承载的操作的授权由调用通道把关（L2）。

### 7.2 缓存

manifest 为低频变更文档；服务端**应当**输出 `ETag` 或 `Cache-Control` 提示，消费方**应当**支持条件请求或定时刷新（具体头部形式由实现自定，一期不作强制）。

### 7.3 版本声明

1. manifest 文档**必须**携带其遵循的本规范版本：OpenAPI 基底文档的 `info.version` 字段**应当**携带 manifest 契约版本（语义化版本），消费方**应当**校验兼容。
2. 契约版本与本规范 `specVersion` 的关系（同一版本号 vs 独立版本号）：**TBD**（TBD-3 一并评审）。
3. 消费方**必须**遵循 must-ignore（§2.2）：不认识的新工具、新扩展字段不得导致解析失败。

## 8. 版本演进

1. 本规范遵循 `VERSIONING.md`（§2.3）。
2. `x-openaiot-*` 扩展字段的新增仅经本规范 MINOR 版本 additive 引入；字段语义不得改变、不得删除（1.0 起）。
3. 渲染产物布局（FC/Claude 数组形态）随各平台公开格式演进；平台格式变更导致渲染规则调整时，以本规范 PATCH/MINOR 跟进，工具名与描述语义不变。
4. manifest 契约的破坏性变更（如隐藏参数语义变化）视同绑定层破坏性变更，走 RFC 通道。

## 附录 A：渲染对照示例（非规范性）

同一 operation（§4.3 的 `list_devices`）经 §5 规则渲染的两份产物对照：

FC 格式：

```json
[
  {
    "type": "function",
    "function": {
      "name": "list_devices",
      "description": "Lists devices page by page. ... To page: pass the previous response's next_cursor until it is empty. Read-only and idempotent.\n\n分页列出设备。……翻页带上一次返回的 next_cursor，直到它为空串。只读、幂等。",
      "parameters": {
        "type": "object",
        "properties": {
          "q":      { "type": "string", "description": "按名称模糊搜索 / Fuzzy search by name" },
          "cursor": { "type": "string", "description": "分页游标 / Pagination cursor" },
          "limit":  { "type": "integer", "default": 20, "minimum": 1, "maximum": 100 }
        }
      },
      "annotations": { "readOnlyHint": true, "idempotentHint": true }
    }
  }
]
```

Claude 格式：

```json
[
  {
    "name": "list_devices",
    "description": "Lists devices page by page. ...（同上拼接串）",
    "input_schema": {
      "type": "object",
      "properties": {
        "q":      { "type": "string", "description": "按名称模糊搜索 / Fuzzy search by name" },
        "cursor": { "type": "string", "description": "分页游标 / Pagination cursor" },
        "limit":  { "type": "integer", "default": 20, "minimum": 1, "maximum": 100 }
      }
    }
  }
]
```

对照要点：工具名/description/schema 两产物逐字节一致（§5.1.3）；`annotations` 扩展键仅出现在 FC 产物（§5.4，供 MCP 适配器透传）；两产物均不含隐藏参数（本例无 `x-openaiot-hidden-params`）。
