## 1. 引言

### 1.1 目的

本规范定义如何把设备能力（经能力注册表组织、原料字段由 L0 能力模型 §8.4 保证）渲染为 **MCP（Model Context Protocol）** 服务端的 tools 接口。它回答：工具如何命名、描述如何写、错误是什么形状、列表如何翻页、协议版本如何协商——使任何符合规范的实现，其 MCP 渲染结果在命名、错误形态、分页行为上互相不可区分。

### 1.2 范围

本规范覆盖：协议版本与基线策略；Streamable HTTP 传输子集；能力注册表 → MCP tools 的机械映射；工具命名约定；annotations 使用；两级错误形态；cursor 分页；输出形态；版本演进条款。

### 1.3 非目标

1. 能力本身的定义——属 L0 能力模型规范。本规范不向 L0 反向引入任何 MCP 依赖（P3：替换 MCP 为其他协议，L0 文档不应有任何变动）。
2. 鉴权、授权、凭据分级与审计——属 L2 授权与安全规范。本规范仅规定"鉴权头与 REST 入口同构"与"错误形态必须能承载授权失败语义"。
3. 工具描述文本的写作细则——属《工具描述写作规范（LLM-first）》（见 §6 引用）。
4. REST/OpenAPI 绑定与 tools manifest 绑定——属各自绑定规范；本规范仅冻结"同源不分叉"条款（§4.1）。
5. MCP 的 resources/prompts/订阅/Tasks 扩展——一期不定义，演进触发条件见 §11.3。

### 1.4 厂商中立声明（规范性）

符合本规范的实现**不得**被要求运行任何特定厂商的云平台、SDK 或许可证。本规范不含、且后续版本不得引入任何将合规性与特定厂商产品绑定的条款。

### 1.5 术语

本规范使用总纲附录 A 的术语。补充：

- **能力注册表（registry）**：能力的单一事实源——把能力元数据（名称、双语描述、输入/输出 schema、标注、权限分级、组合关系）统一登记，并向各绑定入口渲染的机制。本规范只约束其**元数据契约**（§4.2），不约束其内部组织方式。
- **工具（tool）**：MCP 协议中模型可调用的函数单元；本规范中专指注册表中标记为"任务级"（面向 LLM）的能力条目。

## 2. 元约定

### 2.1 约束级别用词

本规范中，**必须（MUST）**、**不得（MUST NOT）**、**应当（SHOULD）**、**不应当（SHOULD NOT）**、**可以（MAY）** 为约束级别用词，含义对齐 RFC 2119/8174 惯例：

- **必须 / 不得**：无条件要求或禁止；违反即不合规。
- **应当 / 不应当**：默认要求或禁止；仅在存在充分理由时可偏离，偏离方必须理解并承担后果。
- **可以**：可选；实现方可自由决定。

### 2.2 前向兼容义务（must-ignore）

1. 客户端与服务端**必须**忽略其不认识的字段、通知与扩展能力，且**不得**因此报错或中断会话。
2. 本规范未覆盖的 MCP 方法，服务端**可以**实现；实现时不得与本规范条款冲突。

### 2.3 规范版本与 MCP 版本的关系

1. 本规范自身版本（`specVersion`）与 MCP 协议版本（`YYYY-MM-DD` 日期版本）相互独立。
2. 本规范头部声明 `mcpBaseline`：渲染结果对齐的 MCP 协议版本。服务端**可以**同时支持其他 MCP 版本（见 §3.2），但基线版本的行为**必须**完全符合本规范。
3. 本规范的演进遵循 `VERSIONING.md`（见 §11.1）。

## 3. 协议版本与协商

### 3.1 基线版本（mcpBaseline）

1. 本版本规范的基线为 **MCP 2025-06-18**：握手制生命周期（`initialize` → `notifications/initialized`）、JSON-RPC 2.0 over Streamable HTTP、`protocolVersion` 在 initialize 中协商。
2. 选择理由（非规范性）：一期参考实现锚定该版本；截至本规范撰写，2025-06-18 世代客户端生态兼容面最广。更新一代（2026-07-28，无握手/`server/discover`/每请求 `_meta` 版本声明）的适配策略见 §11.2。

### 3.2 版本协商行为（2025-06-18 世代）

1. 服务端**必须**实现 `initialize`，并在结果中返回 `protocolVersion`、`capabilities`、`serverInfo`。
2. 客户端请求的 `protocolVersion` 与服务端不一致时，服务端**应当**以其支持的版本回应（MCP 既有协商语义），**不得**静默降级语义。
3. 服务端**应当**同时容忍相邻协议版本客户端的常见差异：未知 `notifications/*` **必须**收下（无 `id` 的通知回 HTTP 202 空体；误带 `id` 的通知形态回空 result），**不得**按未知方法报错。
4. HTTP 层未收到 `MCP-Protocol-Version` 头时，服务端**应当**按 initialize 协商结果处理；无从判断时按 MCP 官方回退规则（缺省假定 2025-03-26）执行。

### 3.3 参考实现注记（非规范性）

首个开源参考实现（Open-AIoT `mcp` 仓库）技术栈已定（2026-09-09 决策）：Go + 官方 MCP Go SDK（github.com/modelcontextprotocol/go-sdk，v1.7.0+ 覆盖 2024-11-05 至 2026-07-28 全部协议版本）。SDK 的多版本支持使"基线 + 双轨"问题从架构负担降级为配置/测试问题；本规范侧的版本策略不因此改变（P1：实现服从规范）。

## 4. 能力注册表 → MCP tools 映射

### 4.1 单一事实源（规范性）

1. MCP tools 与 REST/OpenAPI 端点、tools manifest **必须**从同一份能力注册表渲染；任何绑定**不得**引入注册表中不存在的语义（如仅在 MCP 侧改名、改描述、改参数）。
2. 绑定之间出现分歧时，以注册表元数据为准：改绑定，不改语义。
3. 只有注册表中标记为**任务级工具**（面向 LLM 的聚合能力）的条目**必须**进入 `tools/list`；细粒度端点能力**不得**直接进入 `tools/list`（其作为组合工具的子能力，经 REST/OpenAPI 绑定暴露）。

### 4.2 元数据契约（映射原料）

注册表向本绑定提供以下字段；其中标注"①"者的存在性与稳定性由 L0 能力模型 §8.4 保证，其余为平台级元数据：

| 字段 | 来源 | 含义 |
|---|---|---|
| `name` | ① 动作局部名（L0 §7.4 命名纪律） | 工具名，见 §5 |
| `description {en, zh-CN}` | ① L0 `title`/`description` 双语对象（L0 §11） | 工具描述原料，写作规则见《工具描述写作规范》 |
| `inputSchema` | ① 动作 `input` schema（JSON Schema 2020-12 直出） | 工具入参 |
| `outputSchema` | ① 动作 `output` schema（一等公民，不得省略为"任意 JSON"） | 工具出参，见 §10 |
| `annotations {readOnly, destructive, idempotent, requiresConfirmation}` | ① L0 §8.2 内建标注词汇表 | 工具标注原料，见 §7 |
| `examples` | ① L0 原语 `examples` | 描述示例原料 |
| `scopes` | 平台级（L2 词汇表） | 权限分级；含写控制语义时派生 `readOnlyHint=false` |
| `composedOf` | 平台级 | 组合关系声明；仅作注册表完整性校验，**不暴露**给协议 |

### 4.3 映射规则表（机械映射）

| 注册表字段 | MCP Tool 字段 | 规则 | 级别 |
|---|---|---|---|
| `name` | `name` | 原样 | 必须 |
| `description{en, zh-CN}` | `description` | en 在前、zh-CN 在后，以 `\n\n` 拼接为单一字符串 | 必须 |
| `inputSchema` | `inputSchema` | 原样（JSON Schema 2020-12）；无参数工具使用 `{"type":"object","additionalProperties":false}` | 必须 |
| `outputSchema` | `outputSchema` | 原样；一期参考实现未输出 | 应当（见 §10） |
| `scopes` 含写控制 | `annotations.readOnlyHint` | 派生 `false`；否则 `true`；**所有工具必须输出该键** | 必须 |
| `annotations.destructive` / `annotations.idempotent` | `annotations.destructiveHint` / `idempotentHint` | 值为 `true` 时输出该键；为 `false` 时省略或按实现 SDK 线格式原样输出（见 §7.2） | 必须 |
| `annotations.requiresConfirmation` | — | 不映射为 MCP 字段；其语义**必须**经描述文本的确认指令表达（见《工具描述写作规范》TD-4） | 必须 |
| `composedOf` | — | 不输出 | 不得 |

### 4.4 工具清单行为

1. `tools/list` 返回的工具集**可以**随调用方凭据的授权范围变化（MCP 官方允许：凭据是每请求输入）；**不得**随连接状态或其他请求副作用变化。
2. 工具**必须**按名升序输出（确定性排序，利于客户端缓存与 prompt cache 命中）。
3. 一期服务端**不得**声明 `tools.listChanged` 能力（无订阅通道，见 §11.3）。

## 5. 工具命名约定

1. 工具名**必须**为动词开头的 snake_case。动词白名单：`get_*`（单实体详情）、`list_*`（分页列表）、`control_*`（写控制）、`search_*`（检索）；`create_*`/`update_*`/`delete_*` 为预留动词，一期不使用。新动词仅经规范 MINOR 版本 additive 引入。
2. 字符集遵守 MCP 约束：A–Z、a–z、0–9、`_`、`-`、`.`，长度 1–128，大小写敏感，服务内唯一。一期**不得**使用 `.` 分段命名空间（演进预案见子规划 02 §6.5）。
3. 同一语义的工具名**必须**在 MCP `tools/list`、tools manifest、OpenAPI `operationId` 三处完全一致（§4.1 的直接推论）。

## 6. 工具描述

工具 `description` 文本的写作规则（双语内建、三段式结构、分页教学、破坏性操作确认指令、语义陷阱前置、自声明标注、参数描述、长度纪律）**必须**遵循本仓库《工具描述写作规范（LLM-first）》（`specs/tool-description/v0.1-draft.md`）的全部"必须"级条款。本规范不重复其内容；描述变更视同接口变更，受 `VERSIONING.md` 约束。

## 7. Annotations 使用规范

1. `readOnlyHint`：**所有工具必须**输出（派生规则见 §4.3）。
2. `destructiveHint`、`idempotentHint`：值为 true 时**必须**输出；为 false 时**可以**省略，也**可以**由实现所用 SDK 的线格式原样输出——两者语义等价（MCP 语义：缺省即 false），消费方**不得**依赖 false 值是否显式出现。
3. `openWorldHint`：一期**不输出**该键；其默认值语义是否覆盖全部设备场景（如下行命令触达物理世界是否算 open world）：**TBD**（TBD-1）。
4. **安全前提（规范性复述 MCP 官方立场）**：annotations 是**不可信提示（untrusted hints）**。宿主与客户端**不得**仅凭 hint 跳过人工确认；真正的强制在服务端权限检查（L2 职责）。hint 的用途是宿主 UI 展示建议；模型侧的行为约束以描述文本中的确认指令为准（描述即协议）。
5. 写控制类工具即使标注 `destructiveHint: false`（如"开灯"非破坏性），其描述仍**必须**携带确认指令（见 §6 引用之 TD-4）。

## 8. 错误形态（两级制）

### 8.1 协议错误（Protocol Errors）

请求本身有问题、模型通常无法自纠的错误，**必须**以标准 JSON-RPC error 对象返回：

| 场景 | code | 说明 |
|---|---|---|
| 请求体非合法 JSON | -32700 | Parse error |
| 非合法 JSON-RPC 请求（缺 `jsonrpc`/`method`、批量数组） | -32600 | 一期不支持批量请求，数组一律按此拒绝 |
| 未知方法 | -32601 | `notifications/*` 除外（§3.2.3） |
| `tools/call` 参数形态非法、缺工具名、**未知工具名** | -32602 | message 含自纠线索，如 `unknown tool: xxx` |

HTTP 层一律以 200 承载 JSON-RPC 响应（含错误响应）；`id` 未知时回 `null`。

### 8.2 执行错误（Tool Execution Errors）

执行期错误（权限拒绝、业务校验失败、资源不存在、依赖不可用）**必须**以正常 result + `isError: true` 返回，使模型能读取并自纠：

1. `content` 为单个 text 块，其文本为一个 **problem JSON** 对象，字段与 HTTP 层 problem+json 完全一致：`type`（一期固定 `"about:blank"`）、`title`、`status`（HTTP 语义码）、`code`（业务码，整数）、`detail`。
2. `detail` **必须**含自纠线索（错误可自纠原则）：能区分"参数错了（改参数重试）/ 权限不够（告知用户）/ 资源不存在（重新发现）/ 服务不可用（稍后重试）"。
3. `detail` **不得**泄露内部实现细节（堆栈、SQL、内网地址）；未分类内部错误的 `detail` 一律为通用文案。
4. 业务码表（`code` 字段取值）：一期推荐码表为 `40001`（入参非法）、`401xx`（鉴权类，与 L2 对齐）、`40301`（只读凭据访问写控制能力）、`40401`（资源不存在）、`50001`（内部错误）、`50301`（依赖不可用）。码表是否收编为厂商中立的标准码：**TBD**（TBD-2）；v0.x 期间实现方**必须**保证 `status` 字段语义正确，`code` 取值可以自有但**应当**向推荐码表对齐。
5. 审计与响应换算共用同一状态语义：执行错误的 HTTP 审计状态按 problem JSON 的 `status` 记录。

### 8.3 错误形态示例（非规范性）

```json
{
  "content": [
    { "type": "text", "text": "{\"type\":\"about:blank\",\"title\":\"Not Found\",\"status\":404,\"code\":40401,\"detail\":\"device 12345 not found\"}" }
  ],
  "isError": true
}
```

## 9. 分页约定（cursor）

1. 所有列表型工具的入参**必须**含：`cursor`（string，上一页响应的 `next_cursor`；缺省/空串=首页）、`limit`（integer，页大小）。
2. 响应**必须**为 `{"data": [...], "next_cursor": "..."}` 形态；`next_cursor` 为空串表示没有更多页。
3. 游标为**不透明字符串**：本规范不承诺其编码（参考实现为 base64url 无填充的末条 id）；客户端**不得**解析或构造游标，只能原样回传；服务端对非法游标**必须**返回执行错误（§8.2，400 语义）。
4. 排序**必须**确定（稳定键升序，参考实现按 id）；实现方**应当**以"多取一条"判断尾页。
5. `limit` 缺省值与上限：缺省 20、上限 100、越界 clamp（钳制而非报错）为**应当**级；实现方偏离时**必须**在工具描述中声明实际值。
6. 每个列表型工具的描述**必须**含翻页教学语句（见 §6 引用之 TD-3 的规范句式）。

## 10. 输出形态

1. 成功的 `tools/call` 结果**必须**含单个 text content 块，其文本为结果的 JSON 序列化（与 REST 绑定的响应体语义一致）。
2. 工具**应当**声明 `outputSchema` 并以 `structuredContent` 返回结构化结果；提供 `structuredContent` 时**必须**同时回退输出同一 JSON 的 text 块（MCP 官方兼容要求）。
3. 执行错误的结构化表达（problem JSON 以 `structuredContent` 双写）为本规范 v0.2 候选条款，一期不作为合规要求（见 §8.2 与未决事项）。
4. 结果中**不得**包含凭据、内网地址等敏感信息；面向模型的文本**应当**经过输出净化（MCP 官方安全要求的复述）。

## 11. 版本演进与兼容

### 11.1 规范演进

1. 本规范遵循 `VERSIONING.md`：主版本内只增不删；必填字段冻结；弃用有公示期；实现方必须忽略未知字段；破坏性变更仅经 RFC 通道。
2. 本规范头部携带 `specVersion` 与 `mcpBaseline`；两者独立演进（§2.3）。
3. 工具描述文本、错误 `detail` 文案的变更视同接口变更，纳入变更记录；但错误文案的措辞润色（不改变语义类别）属于 PATCH 级。

### 11.2 MCP 2026-07-28 世代适配

1. 2026-07-28 世代的适配（`server/discover`、每请求 `_meta` 版本声明、移除握手与协议级 session）**必须**以本规范的 MINOR 版本引入，并同步更新头部 `mcpBaseline`（或改为多基线声明，具体形式随该 MINOR 评审确定）。
2. 适配的触发条件（非规范性，决策见子规划 02 §9 第 1 条）：主流客户端生态对 2026-07-28 的支持度经 Phase 1 实测确认。参考实现侧的官方 SDK 多版本支持（§3.3）使该适配无需实现分叉。
3. 适配时**不得**改变第 4–10 章的工具语义（命名、映射、错误、分页、输出）——传输与生命周期机制的演进不触及工具语义，这是本规范的分层承诺。

### 11.3 暂不定义的能力与触发条件

以下 MCP 能力本版本**刻意不定义**；触发条件（任一满足即启动相应 MINOR 评估，决策见子规划 02 §6.1/§6.2/§6.4）：

| 能力 | 触发条件 |
|---|---|
| SSE 流 / 订阅（`subscriptions/listen` 或 2025-06-18 世代的资源订阅） | 设备实时数据订阅（遥测面板、告警推送）需求出现；或 server→client 主动通知需求（tools/list 热变更）；或首个连接器伙伴明确要求 |
| resources / prompts | 产品文档/设备手册接入需求；prompts 待 Skill 生态规范（子项目 05）定稿后联合评估 |
| Tasks 扩展（长耗时任务） | 一期以"句柄 + 轮询工具"表达长任务（如固件升级：`start_*` 返回任务句柄、`get_*_status` 轮询）；Tasks 扩展在主流客户端落地且需要中途取消/输入时评估 |
| 批量请求 | 无计划；出现真实批量调用场景再评估 |

句柄设计义务（一期长任务即适用）：句柄**必须**不透明、有界生存期、过期返回可自纠错误、每次调用重新鉴权。
