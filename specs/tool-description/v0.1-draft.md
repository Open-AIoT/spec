## 1. 引言

### 1.1 目的

LLM 不读规范文档，只读工具描述（description）。凡需要模型遵守的行为约定——分页怎么翻、控制前要不要问用户、返回值的真实含义——只在规范里写而不进描述，等于不存在（**描述即协议**）。本规范把"写给模型看的工具描述"确立为可评审、可检查的标准条款，适用于一切进入 LLM 视野的工具文本：MCP `tools/list` 的 `description`、tools manifest（function-calling（FC）格式与 Claude tool-use 格式）的描述字段，以及未来协议绑定的等价字段。

### 1.2 适用范围与分工

1. 本规范约束 **L1 渲染产物的描述文本**（工具描述、参数描述）。
2. 模型层（L0）的 `title`/`description` 双语对象的结构与存在性由《设备能力模型》§11 保证；本规范约束绑定层把原料**改写为面向 LLM 的描述**时的写法（L0 §8.4 预留的确定性映射由本规范落地为写作纪律）。
3. 描述文本是接口的一部分：其变更视同接口变更，受 `VERSIONING.md` 约束（措辞润色不改语义者为 PATCH 级）。

### 1.3 厂商中立声明（规范性）

本规范不含、且后续版本不得引入任何将合规性与特定厂商产品绑定的条款。条款中的示例均为通用设备场景，不指向特定平台。

### 1.4 受众

本规范的读者包括：工具作者（撰写/修订描述时逐条对照第 3 章）；绑定实现者（渲染 MCP tools、tools manifest 时验证产物满足第 3 章）；评审者（按 §4 lint 清单评审）；自动化检查工具的作者（§4 清单即检查项规格）。

### 1.5 命名说明（P10）

本项目与任何同名/近名公司无关联；项目名写作"开放AIoT（Open AIoT）"。本规范以中立术语 **function-calling（FC）格式** 指代业界公开发布的 `{"type":"function","function":{...}}` 工具清单 JSON 格式，不引用其发布方名称。

## 2. 元约定

### 2.1 约束级别用词

**必须（MUST）**、**不得（MUST NOT）**、**应当（SHOULD）**、**不应当（SHOULD NOT）**、**可以（MAY）** 为约束级别用词，含义对齐 RFC 2119/8174 惯例：必须/不得为无条件要求或禁止；应当/不应当仅在存在充分理由时可偏离；可以为可选。

### 2.2 条款编号

第 3 章八条条款编号 TD-1～TD-8，供 lint 工具（§4）与评审引用。每条含"要求 + 正例 + 反例"；示例中的工具名为示意，不构成工具集承诺。

### 2.3 与绑定规范的关系

1. 各绑定规范（MCP 绑定、REST/OpenAPI 绑定、tools manifest 绑定）以引用方式继承本规范，**不得**在各自文档中另立描述写作规则；绑定特有的描述要求（如 MCP 的描述拼接格式）由绑定规范定义，本规范定义与协议无关的写作纪律。
2. 本规范与绑定规范冲突时，以绑定规范的协议强制性要求为准（协议字段格式不可协商），其余一律以本规范为准。
3. tools manifest 的 OpenAPI profile 形态目前为**推荐方向，Phase 0 验证**（子规划 02 §9 开放问题 7）；无论其形态如何落地，`x-` 扩展中的 LLM 描述字段（推荐名 `x-openaiot-llm-description`）的内容**必须**遵守本规范。

## 3. 写作条款

### 3.0 通则

1. 八条条款适用于**所有**进入 LLM 视野的工具文本，与绑定协议无关；新协议绑定的描述字段默认继承本规范全部条款。
2. 条款之间相互支撑而非互相替代：双语内建（TD-1）要求其余各条的任何行为约定在两种语言中同时出现；长度纪律（TD-8）的删减顺序不得触及其他条款的强制内容。
3. 条款中的"范本/规范句式"来自首个参考实现中已验证的实践（经真实模型联调）；修改范本视同条款变更，走 `VERSIONING.md` 流程。
4. 描述的最终读者是模型而非人：一切措辞以"模型能否据此做出正确的调用决策"为检验标准，而非"人读起来是否优雅"。

### TD-1 双语内建

**要求**：

1. 每个工具描述**必须**中英双语内建：英文在前、中文在后，段落间以 `\n\n` 拼接；行内双语短语以 ` / `（空格斜杠空格）分隔。
2. 两种语言的信息**必须**对等——不得出现"中文详细、英文一笔带过"或反之；行为约定（确认指令、分页教学、错误语义）在两种语言中逐条对应。
3. 语言标记与结构对应 L0 §11：`en` 必须存在，`zh-CN` 应当存在。

**正例**（节选自参考实践 `list_devices`）：

> Lists devices on the platform page by page. Use when the user asks what devices exist, to find a device by name/MAC (q), or to discover device IDs for get_device_overview / control_device. [...]
>
> 分页列出平台上的设备。什么时候用：用户问"有哪些设备"、要按名称/MAC 找某台设备、或需要拿到设备 id 供 get_device_overview / control_device 使用。[...]

**反例**：英文段完整给出翻页方法与权限要求，中文段只写"列出设备"——中文使用者语境下的模型将丢失行为约定。

### TD-2 三段式结构

**要求**：工具描述**必须**按三段组织：

1. **做什么**——一句话说明功能（对应动词白名单语义）；
2. **什么时候用**——列举触发场景，**应当**包含自然语言锚点（如"用户问『有哪些设备』时用本工具"），并指出与相邻工具的分工（何时不用本工具、改用哪个）；
3. **行为与边界**——错误语义（什么情况返回 not_found 等）、权限要求、幂等性、返回值关键语义。

**正例**（结构标注自参考实践 `get_device_overview`）：

> [做什么] Returns the full picture of one device in a single call: its profile plus its shadow. [什么时候用] Prefer this over separate detail/shadow lookups when inspecting a device or answering how a device is doing. [行为与边界] Fails with a not_found error when the device does not exist; shadow is null when the device has never reported state. Read-only and idempotent.

**反例**：仅写"获取设备概览。/ Get device overview."——模型无从判断它与 detail、shadow 类工具的分工，会在多个候选工具间误选。另一常见反例：三段内容挤在一句里（"获取设备概览，用户问设备怎么样时用，设备不存在报错"）——信息齐全但缺分工锚点与相邻工具指引，模型在多工具场景下的选择准确率仍显著低于完整三段式。

### TD-3 分页教学

**要求**：每个列表型工具的描述**必须**包含翻页方法的教学语句，使用规范句式（或信息完全等价的表述）：

> To page: pass the previous response's next_cursor until it is empty.
> 翻页：带上一次响应的 next_cursor 再请求，直到 next_cursor 为空。

分页参数（cursor/limit）的取值约束**必须**同时写入参数描述（见 TD-7）。模型不知道分页协议，描述是唯一教学渠道；漏写翻页教学的列表工具视为不合规。

**反例**：描述写"分页列出设备"但不给翻页方法——模型会猜测 `page=2`、`offset=20` 等不存在的参数。

### TD-4 破坏性/写控制操作确认指令

**要求**：

1. 一切会改变真实设备状态的工具，其描述**必须**包含显式的人在环路确认指令，使用规范范本（可按场景适配，但"说明目标与内容、获得明确同意、不得自行决定"三要素不得删减）：

> WARNING: this changes the state of a physical device — BEFORE calling, always tell the user the target device and the exact command, and call only after explicit approval; never decide to execute on your own.
>
> ⚠️ 这会改变真实设备的状态：调用前必须先向用户说明目标设备与确切命令内容并获得明确同意，不得自行决定执行。

2. 确认指令**必须**同时出现在英文与中文段（TD-1）。
3. 确认指令是模型侧的行为约束；它与协议标注（`annotations`）职责不同——标注给宿主 UI，指令给模型——两者**必须**双写，不得互相替代。服务端的强制确认/授权语义属 L2，不依赖本条。
4. 权限要求**应当**在行为与边界段写明（范本："Requires the control scope (read-only credentials are rejected). / 需要 control 权限（只读凭据会被拒绝）。"）。

**反例**：写控制工具只标 `destructiveHint`/`readOnlyHint=false` 而描述中无确认指令——不读标注语义的宿主将让模型直接执行物理操作。

### TD-5 语义陷阱前置

**要求**：返回值与字段的真实含义中，凡是"想当然会理解错"的，**必须**写进描述：

1. 异步/投递类返回值的真实语义（范本："sent=1 means the command was delivered to the device's server node, not that the device executed it. / 返回 sent=1 仅表示命令已投递到设备所在节点，不代表设备已执行。"）；
2. 可空字段的 null 语义（范本："shadow is null when the device has never reported state. / 设备存在但从未上报过状态时 shadow 为 null。"）；
3. 部分失败与静默丢弃语义（范本：非法命令键被忽略、全部非法才报错）；
4. 结果集的范围限制（范本："Results are limited to the credential's bound workspace. / 结果只含当前凭据绑定工作台的 ……"）；
5. 时间字段的格式与时区语义（凡出现时间戳，**应当**写明格式约定——对齐 L0 §5.3 的 RFC 3339 纪律，避免模型按 Unix 秒猜测）。

判断"什么算陷阱"的经验法则：如果一个字段的值**不能**按其名称的常识理解（投递≠已执行、null≠错误、人类可读文案≠机器码），它就是陷阱，必须前置说明。

**反例**：控制类工具不说明 sent 语义——模型会把"已投递"当作"已执行"向用户汇报，构成对物理世界状态的虚假陈述。

### TD-6 自声明标注

**要求**：描述末尾**必须**以固定短语声明工具的行为属性，与协议标注双写（标注给 UI，文本给模型）：

- 只读且幂等：`Read-only and idempotent. / 只读、幂等。`
- 非幂等：`Not idempotent. / 非幂等。`
- 只读但非幂等（如触发一次检索任务）：`Read-only but not idempotent. / 只读、非幂等。`

短语置于行为与边界段的末尾，逐字使用或逐字翻译，不自由发挥。

**反例**：描述通篇不提幂等性，仅在 annotations 里标 `idempotentHint`——模型在需要重试时无法判断重试是否安全。

### TD-7 参数描述写法

**要求**：`inputSchema` 中每个参数的 `description` **必须**包含：

1. 双语说明（行内 ` / ` 分隔）；
2. 取值约束（范围、枚举含义、单位；schema 已有的约束仍**应当**在文本中复述要点，因为部分宿主不把完整 schema 喂给模型）；
3. **发现路径**：参数的合法值如何获得（范本：id 参数写"discover via list_devices by name/MAC / 可用 list_devices 按名称/MAC 查到"——把工具间调用链教给模型）；
4. 参数为必填时，**应当**在描述中体现必填性（FC 接口在 API 层硬校验 required，Claude 形态无统一硬约束、靠描述软约束——描述双写是两形态下的共同兜底）。

**正例**：

> `"id": { "type": "integer", "format": "int64", "description": "设备 ID（可用 list_devices 按名称/MAC 查到）/ Device ID (discover via list_devices by name/MAC)" }`

**反例**：`"limit": {"type":"integer"}` 无描述——模型不知道缺省值与上限；或 id 参数只写"设备 ID"——模型不知道去哪里获得合法 id，会编造。

### TD-8 长度纪律

**要求**：

1. 工具描述以英文部分计，**应当**不超过 120 词（另加对等中文）；参数描述单行**应当**不超过 80 字符（双语合计）。
2. 超限时**必须**按以下顺序删减：形容词与修辞 → 重复 schema 已表达的约束 → 场景列举的尾项；**不得**删减行为约定（确认指令、分页教学、错误语义、null 语义）。
3. 理由（非规范性）：描述进入每次模型调用的上下文，按 token 计费并挤占有效上下文窗口；工具集规模增长时长度纪律是防上下文污染的第一道闸门（与子规划 02 §6.5/§6.6 的策展纪律配合）。

**反例**：描述以"This powerful and flexible tool is designed to help you easily..."开头——全部是可删的修辞。

## 4. 符合性检查清单（lint）

规范的落地依赖检查而非自觉。以下清单**应当**实现为参考实现 CI 的自动检查（Phase 1 起）；每一项对应条款编号：

| # | 检查项 | 条款 |
|---|---|---|
| L1 | 描述含英文段与中文段（`\n\n` 分隔），两段行为约定逐条对应 | TD-1 |
| L2 | 描述可切分出"做什么/什么时候用/行为与边界"三段 | TD-2 |
| L3 | 列表型工具（`list_*`）描述含规范翻页句式 | TD-3 |
| L4 | 写控制类工具描述含确认指令三要素（说明目标与内容/明确同意/不得自行决定），中英双份 | TD-4 |
| L5 | 含可空字段、投递类返回值的工具，其 null/sent 语义在描述中出现 | TD-5 |
| L6 | 描述末尾含固定自声明短语，且与 annotations 一致 | TD-6 |
| L7 | 每个参数有双语描述；id 类参数含发现路径；必填参数描述体现必填性 | TD-7 |
| L8 | 英文段 ≤ 120 词 | TD-8 |

lint 检查不通过的工具**不得**进入参考实现的发布工具集；对"应当"级条款的偏离**必须**在评审记录中写明理由（§2.1 偏离义务）。

检查自动化的边界：L1/L3/L4/L6/L7 可完全机械化（句式匹配与结构检查）；L2/L5 需要语义判断，v0.x 阶段以人工评审为主、模型辅助评审为辅（评审提示词范本待 Phase 1 随 lint 工具一同发布）。lint 工具本身开源，作为 manifest/mcp 仓库的 CI 组件。

## 附录 A：完整合规示例（非规范性）

以下为一个写控制类工具的完整描述与入参 schema，段落功能以【】标注（标注本身不进描述文本）。该示例同时满足 TD-1～TD-8 与 MCP 绑定规范 §4.3 的映射要求：

```json
{
  "name": "control_device",
  "description": "Sends a control command to one real physical device, e.g. {\"power\":1} (keys are command/property names defined by the product; unknown keys are dropped). 【做什么】\nUse this only when the user has asked to change a device's state; to inspect a device, use get_device_overview instead. 【什么时候用，含与相邻工具的分工】\nWARNING: this changes the state of a physical device — BEFORE calling, always tell the user the target device and the exact command, and call only after explicit approval; never decide to execute on your own. Requires the control scope (read-only credentials are rejected). sent=1 means the command was delivered to the device's server node, not that the device executed it. Fails with not_found when the device does not exist. Not idempotent. 【行为与边界：确认指令 + 权限 + 语义陷阱 + 自声明】\n\n向一台真实物理设备下发控制命令，如 {\"power\":1}（键为产品定义的命令/属性名，非法键被忽略）。\n仅当用户要求改变设备状态时使用本工具；查看设备状况请改用 get_device_overview。\n⚠️ 这会改变真实设备的状态：调用前必须先向用户说明目标设备与确切命令内容并获得明确同意，不得自行决定执行。需要 control 权限（只读凭据会被拒绝）。返回 sent=1 仅表示命令已投递到设备所在节点，不代表设备已执行。设备不存在返回 not_found。非幂等。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "id": {
        "type": "integer",
        "format": "int64",
        "description": "设备 ID（必填；可用 list_devices 按名称/MAC 查到）/ Device ID (required; discover via list_devices by name/MAC)"
      },
      "command": {
        "type": "object",
        "additionalProperties": true,
        "description": "命令内容（必填）：键=产品命令/属性名，值=参数，如 {\"power\":1}；非法键被忽略 / Command payload (required): keys are product command/property names, e.g. {\"power\":1}; unknown keys are dropped"
      }
    },
    "required": ["id", "command"]
  },
  "annotations": { "readOnlyHint": false }
}
```

对照检查：双语对等（L1）；三段齐全（L2）；确认指令三要素中英双份（L4）；sent 语义与非法键丢弃语义前置（L5）；末尾固定短语（L6）；参数双语 + 必填体现 + 发现路径（L7）；英文段约 110 词（L8）。

## 附录 B：规范句式速查（规范性——句式文本本身）

以下句式为各条款的推荐定稿文本；实现方**可以**按场景适配，但标注"要素不得删减"的除外。

| 用途 | 句式 | 条款 |
|---|---|---|
